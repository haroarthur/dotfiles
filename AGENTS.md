# dotfiles

Home configuration for two machines - Windows + WSL Ubuntu, and a Mac - cloned to `~/.dotfiles`.
[README.md](README.md) is the reader's entry point; this file is what an agent needs before editing.

- Machine-wide agent rulebook: [home/AGENTS.md](home/AGENTS.md)
- Host compositions: [hosts/](hosts/). Packing: [pkgs/](pkgs/). Every file's header is one sentence saying what it owns
- [pkgs/shell.nix](pkgs/shell.nix) is the one module BOTH hosts import; anything WSL-only about the shell (bash login shell, OSC 7) belongs in [pkgs/shell-wsl.nix](pkgs/shell-wsl.nix), which only `hosts/wsl-ubuntu.nix` imports
- **Use official installers for tools that ship them and host packages for plain packages; keep custom Nix integration only where there is a concrete blocker, named in the file that keeps it.** Nothing is hand-pinned; Herdr's binary comes from its own installer and what [pkgs/herdr/module.nix](pkgs/herdr/module.nix) keeps is the part a package cannot bring - the service, the pane slice and the pane shell, with the unit execing `~/.local/bin/herdr`. No new wrapper, control plane or converger without naming the blocker
- **[windows.ps1](windows.ps1) is one self-contained file** and must stay that way: it must still run with no clone beside it, so it may never read a sibling, which is why the two files it writes are text inside it. It does five things - `wsl --install`, WezTerm, the font, `.wslconfig`, and the `.wezterm.lua` that loads this clone's config. `$distro` is the single source for the distro name inside the script; every WSL call targets it explicitly and the generated WezTerm stub receives it from there. The README mirrors that exact name in the commands a person runs. The documented order runs it OUT of the clone, where it is a file on the WSL share and PowerShell refuses it under anything stricter than `Bypass` - [README.md](README.md#the-windows-side) carries the exact two lines and, honestly, which of them were executed here and which were not
- **[tools.list](tools.list) owns the doctor's tool checks and `install-tools.sh`'s npm inputs.** Its header defines the four-column schema, including checks for Nix packages. Never grow a second tool list in either script. A harness plugin (compact-adviser) is not a tool and never a row there - [README.md](README.md#compact-adviser)
- **Skills are not in this repository.** They live in `haroarthur/agents` (private), checked out at `~/.agents`. This repo declares one pointer, `~/.claude/skills` -> `~/.agents/skills`, in [hosts/common.nix](hosts/common.nix); Codex reads `~/.agents/skills` natively. Never add a `home/skills/` or a second skill list here
- Every PR body reports the total Nix+shell line count before and after, computed as `git ls-files '*.nix' '*.sh' | xargs wc -l | tail -1`; never claim "lean" unless that number went down

A fresh machine comes up in two phases, and the split is load-bearing: **phase 1 is the machine and needs no login** (public inputs only - Determinate Nix, this flake, the switch, the tool installers), **phase 2 is the account** (the private `~/.agents` skills checkout, Firstmate) and starts at `gh auth login`, after which `install-tools.sh` does the rest itself. The Windows side is phase 1: [windows.ps1](windows.ps1) needs no login either. Keep it that way: nothing that needs a credential belongs in phase 1, which is what lets CI run the entry scripts. The README's human path logs in BEFORE the bootstrap, because the clone of a private repo needs it - that is an order for a person, not a change to this contract, and it only means phase 2's work lands inside phase 1's last step - [README.md](README.md#a-fresh-machine-in-order), [.github/workflows/bootstrap-check.yml](.github/workflows/bootstrap-check.yml).

`./doctor.sh` is read-only and safe to run any time (it opens no Herdr socket); it is **advisory on purpose** - never wire it into `rebuild.sh` or `bootstrap.sh` as a gate. Its verdicts hold phase 1 apart from what a login or another OS owns, so **phase-1 FAIL is the only count that means anything**; a `phase 2` or `skip` line is not a red box. `./install-tools.sh` runs every installer, including Herdr's, no-mistakes, the one `sudo apt-get` (Chrome) and, once `gh auth status` succeeds, the `~/.agents` clone; each tool installs only when absent, so an installed no-mistakes daemon is never restarted by a rerun. `gh auth login` is the one thing a person types. Claude's and Pi's `settings.json`, like the Herdr config, are **seeded and never linked** ([hosts/common.nix](hosts/common.nix)): both programs rewrite them, and a link put every rewrite in the git tree. Never turn them back into `home.file` entries.

Never run `bootstrap.sh` / `rebuild.sh` / `home-manager switch` without being told to. Neither script takes a flag or an environment variable: what protects a live host is the `wsl-ubuntu-safe` guard both build before they switch ([flake.nix](flake.nix)), and a hand-run `home-manager switch` goes around it. `bootstrap.sh` is the day-one path for a NEW box; a host already running this changes only through `rebuild.sh`.

Prove a change by building, not switching: `nix flake check`. A green build alone says nothing about the profile - `wsl-ubuntu-safe` is the check that does. A refactor must also leave the live host untouched: build the generation before and after and compare the `herdr.service` and `herdr-panes.slice` unit files byte for byte, because the running server is never restarted by a switch and a changed unit is what a later restart would adopt. CI runs that same check on every pull request and every push to `main` ([.github/workflows/flake-check.yml](.github/workflows/flake-check.yml)). The header of [.github/workflows/bootstrap-check.yml](.github/workflows/bootstrap-check.yml) owns the trigger policy for the second, opt-in workflow, which runs the entry scripts themselves on clean runners; it is never a required check, so a skip never blocks a merge. Run `nix fmt` before committing; new files must be `git add`ed before Nix can see them.

## Firstmate on a new machine

Day-one Firstmate install for a **new** Mac or second WSL is documented in [README.md](README.md#skills-and-firstmate) (clone `kunchenguid/firstmate`, launch one co-primary). Never clone over a live Firstmate home; never `npx skills add` Firstmate. That home's records come back from the private `haroarthur/fleet-records`, one branch per home, by cloning the branch into a `data/` that does not exist yet - [README.md](README.md#records-for-a-fresh-firstmate-home). Git's own refusal to clone into a non-empty path IS the no-clobber guarantee: never reach past it into a home that already has records.
